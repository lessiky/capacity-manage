## 2. 本阶段发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | `alert.OnMissing` 去重按 `trigger_at`(当前时间) 比对业务日窗口，永远匹配不到 | 缺数告警每日重复生成 | 去重键改 `last_value_at`（存业务日）；补单测覆盖重复执行 |
| 2 | `data/handler.timeRange` 中 `to` 日期为独占边界（`ts < to` 且 to 未 +1 天） | 查询"当天"日内数据恒为空（from=to=今天 → 空区间） | 显式 `to` 日期解析后 +1 天（含边界）；默认值语义不变 |
| 3 | `persistence.DataSource` 的 `LastSuccessAt` 字段被同行注释吞掉，模型实际无此字段 | GORM 无法读写 last_success_at（生产 map 更新碰巧可用，模型路径失效） | 恢复字段定义 |
| 4 | `CollectTaskLog.ErrMsg` GORM 列名推导为 `err_msg`，与 DDL `error_msg` 不一致 | 任务日志错误信息 struct 扫描恒为空 | 模型显式 `gorm:"column:error_msg"` |
| 5 | 引擎 `RunPreview` 路径未回填 `cleanValue` | 预览结果清洗值恒 null，无法核对取值 | CleanPhase2 后统一回填 |
| 6 | 测试装置（testutil）用默认 GORM 命名（复数表名），与生产 `SingularTable:true` 不一致 | sqlite 建表 sys_params 等，参数/表名错位导致重试测试假挂起 | testutil 统一 `NamingStrategy{SingularTable:true}`；新增通用 `DBHarness` |
| 7 | `Handler.Trigger` 手工触发在 goroutine 中复用 `c.Request.Context()` | HTTP 响应返回后 context 立即取消，耗时较长的执行（如 Python 沙箱）被中断（"context canceled"） | 改用独立后台 context，时长由 `Engine.RunTimeout()` 按 超时×(重试+1)+间隔×重试 精确推导 |

## 5. 遗留与 M3 衔接

- "试点系统数据连续 1 周自动采集无中断"验收需真实试点源（Oracle/MySQL 只读账号 + SFTP 日志服务器）接入后观察，dev 环境以 local 日志源 + 示例脚本替代验证链路；
- 缺数"趋势图标记"的数据支撑已就绪（`alert_type=missing` 记录业务日），展示在 M3 指标详情/趋势页（WBS 3-4）接入；
- 监控大盘 KPI 卡与图表仍为占位（M4 FR-MON-01/02）；日汇总/水位/日报为 M3（3-1/3-2/3-3）；
- Python 脚本沙箱网络隔离依赖部署层（Docker network/防火墙），dev 环境 worker 容器可访问宿主网络，生产需按契约 §1.2 收紧；
- 失败重试间隔 60s 默认值下，最坏重试耗时 ≈ 3×间隔 + 4×超时上限，建议对慢数据源调大 `flow_timeout_seconds` 时同步评估调度窗口。
