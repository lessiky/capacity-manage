# 容量管理平台运维手册（二期）

| 项 | 内容 |
| --- | --- |
| 版本 | V2.0（2026-10-22） |
| 适用读者 | 平台运维、DBA、SRE |
| 部署形态 | Docker + Docker Compose（MVP 单节点；双活为目标形态，预留 K8s） |

## 1. 部署架构与组件

| 组件 | 端口 | 说明 |
| --- | --- | --- |
| frontend | 80 | Nginx 静态资源 + 反代 `/api` → backend |
| backend | 8080 | Go 服务（API + 调度器 + 判定 + 报表） |
| worker | 9100 | Python 沙箱 Worker（独立进程池，池大小可配） |
| postgres | 5432（内网） | 主数据库（按日分区表 metric_value_day/metric_value_rt） |
| redis | 6379（内网） | 会话（sess:<jti>）、登录失败计数、缓存 |
| 外部：业务源库 | — | SQL 采集源（只读账号）；日志源（本地/SFTP） |

- 容器编排：`deploy/docker-compose.yml` + 环境文件 `deploy/env/<APP_ENV>.env`（dev/sit/uat/prod）；
- 启动顺序：postgres/redis 健康 → backend-migrate（`capacity-server migrate && seed`，幂等）→ backend → worker → frontend；
- 数据库迁移：GORM AutoMigrate + 版本化 seed（`db/` 目录），migrate 容器随 `up -d` 自动执行，可重复运行。

## 2. 环境配置要点（env）

| 变量 | 说明 | 生产要求 |
| --- | --- | --- |
| `JWT_SECRET` | JWT HS256 密钥 | 强随机、独立于开发值、定期轮换 |
| `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME` | Postgres 连接 | 强口令、最小权限账号 |
| `REDIS_ADDR/REDIS_PASSWORD` | Redis 连接 | 建议开启密码 |
| `APP_CRED_KEY` | 数据源凭据 AES-256-GCM 主密钥（64 hex） | **独立配置、离线保管、支持轮换**（轮换需重新加密存量数据源凭据，见 §6） |
| `WORKER_URL` | backend → worker 内网地址 | 仅内网可达 |
| `WORKER_TIMEOUT_SEC` | 沙箱任务超时（默认 310s，脚本 300s 强杀） | 按最大脚本耗时调整 |
| `AI_ENABLED/AI_BASE_URL/AI_MODEL/AI_API_KEY/AI_TIMEOUT_SEC` | AI 适配器（可插拔） | 不启用则置 false；API Key 独立保管；预测和事件功能在 AI 关闭时仍可用 |
| `SCHEDULER_ENABLED` | 调度总开关 | 故障应急可置 false 停止调度 |
| `FILE_ROOT` | 日报文件落盘目录 | 独立卷、纳入备份/容量监控 |
| `LOG_LEVEL` | 日志级别 | 生产 info |

热配置（DB + 本地缓存 + 变更通知，免重启）：`sys_param` 表参数，如 `daily_summary_time`（默认 00:10）、`daily_report_time`（默认 00:30）、`daily_forecast_time`（默认 00:45）、`rt_retain_days`（默认 90）、`day_retain_days`（默认 1095）、`login_fail_limit=5`、`login_lock_minutes=15`、调度并发（默认 8）。

## 3. 备份与恢复

- **备份**：Postgres 每日全量备份（`pg_dump` 或卷级快照），保留 ≥30 天；`FILE_ROOT`（日报文件）随备份；
- **恢复演练**：上线前至少 1 次、此后每季度 1 次"按日恢复"演练（恢复到临时实例，核对 `metric_value_day` 目标业务日行数与日报文件）；
- **恢复步骤（摘要）**：
  1. 停止 backend（`SCHEDULER_ENABLED=false` 或 `docker compose stop backend worker`）；
  2. 恢复目标业务日之前的备份到数据卷/新实例；
  3. 校验：`SELECT count(*) FROM metric_value_day WHERE biz_date = '<目标日>'`、迁移版本、日报文件；
  4. 启动服务；调度自动补跑（日汇总/日报幂等）。
- **注意**：迁移脚本版本化（`backend/internal/persistence` + `db/`），恢复跨版本时须按 §5 升级流程处理，禁止直接混用旧备份与新二进制而不评估迁移差异。

## 4. 监控与告警接入

- **平台自检页**（系统管理 → 平台自检，`GET /admin/health`）：backend/worker/storage/调度/数据源健康 —— 运维每日检查第一项；
- **接入运维监控（必接）**：
  1. 进程：容器存活/重启次数（docker healthcheck：backend :8080 健康端点、worker :9100/v1/health）；
  2. 接口：/api 5xx 比率、P95 延迟；
  3. 磁盘：postgres 数据卷、`FILE_ROOT`、worker 工作目录（日表增长 ~5 万行/日/指标量）；
  4. 调度：`daily_summary_log`（status=failed 告警）、采集任务当日 failed/timeout 数量、`collect_task_log`；
  5. 数据源：`data_source.health_fail_streak` 连续失败；
- **日志**：backend 结构化日志（slog JSON，含 traceId）；worker 执行日志（stdout/stderr 尾部入库 `collect_task_log`）；操作日志（平台内，`/admin/operate-logs`）。

## 5. 升级与回滚

### 5.1 升级流程

1. 变更单：版本号、发布说明、影响范围、回滚点；
2. 低峰窗口：`docker compose pull`（或替换镜像）→ `docker compose up -d`；
3. migrate 容器自动执行数据库迁移（幂等）；
4. 验证：平台自检页全绿 + 冒烟（登录/大盘/日报/一条采集触发）；
5. 观察 30 分钟：任务成功率、接口 5xx、日志错误。

### 5.2 回滚预案

- **镜像回滚**：旧版本镜像保留（tag 不删除）；`IMAGE_TAG` 切回旧 tag → `up -d`；
- **数据回滚**：仅"可加不可减"的迁移（新增列/表）无需回滚数据；若迁移含破坏性变更，必须使用 §3 备份恢复至升级前业务日；
- **回滚触发条件**：P0 缺陷且 30 分钟内无法热修；接口 5xx >1% 持续 10 分钟；调度全部失败。

## 6. 凭据密钥管理

- 数据源凭据：`APP_CRED_KEY`（AES-256-GCM）加密落库，格式 `enc.v1.*`；页面/日志/导出恒脱敏；
- **密钥轮换**：生成新 key → 后台重新加密存量 `data_source.config`（运维脚本，二期提供一键工具；一期手工逐条重存）→ 更新 env 滚动重启；
- 轮换周期建议：每年或人员变动时；密钥离线双人保管。

## 7. 二期调度与任务

| 任务 | 触发 | 运维检查 |
| --- | --- | --- |
| 日汇总 | `daily_summary_time`，默认 00:10 | `daily_summary_log` 状态、是否有当日数据 |
| 预测 | `daily_forecast_time`，默认 00:45，要求在日汇总 success/partial 后运行 | `forecast_run` 状态、metrics_total/done/skipped、AI 降级状态 |
| 报表订阅 | 每分钟检查到期任务 | `report_run`、通知日志、下次运行时间 |
| 归档 | 调度检查保留期，也可管理员手工运行 | `metric_archive_run/index` 状态、文件大小和失败原因 |

预测重跑：

```text
POST /api/v1/forecasts/recompute?date=YYYY-MM-DD
```

重跑是幂等的；同一输入、模型和事件版本结果应一致。AI 失败不等于预测失败，先确认统计结果已产出。

## 8. 通知与订阅运维

- 渠道健康：检查 SMTP/IM/Webhook 连通性、认证、TLS 和目标白名单；
- 投递日志：通知日志的状态、尝试次数、错误摘要、幂等键；
- 失败重试：1/5/30 分钟；三次失败后产生 `notify_fail` P4 渠道异常告警；
- 重复发送：检查去重窗口和级别是否变化；升级后允许再次通知是预期行为；
- 静默：静默窗口内日志应显示抑制原因，告警和通知记录不得丢失。

应急隔离：

1. 在“通知订阅”停用问题渠道；
2. 保留渠道配置与发送日志；
3. 修复网关或凭据后执行渠道测试；
4. 对需要补发的失败日志使用手工重试；
5. 确认去重键生效，避免重试造成通知风暴。

## 9. 开放 API 运维

- Key 巡检：`api_key` 的状态、过期时间、scope、系统范围、限流和最近调用；
- 调用审计：`api_call_log` 中 `allowed=false` 的比例、拒绝原因、来源 IP、P95 延迟；
- 签名：检查 `X-Cap-Timestamp`、`X-Cap-Nonce`、`X-Cap-Signature` 和服务器时间；
- nonce 存储：Redis 键 `apikey:nonce:{keyId}:{nonce}`，TTL 10 分钟；Redis 不可用时签名请求应 fail closed；
- 限流：Redis 键 `apikey:rate:{keyId}:{yyyyMMddHHmm}`，固定窗口计数；Redis 故障时按可用性优先放行，但审计继续记录；
- 密钥泄露：立即轮换 Key，旧 secret 生效即失效；检查 `api_call_log` 的异常来源。

## 10. 预测、事件因子与 AI

- 统计预测是主路径；AI 仅作受限修正；
- AI 不可用、超时、401/429 或输出非法时，`forecast_ai_adjustment.status=invalid`，主结果保持统计预测；
- 超幅 AI 调整状态为 `oversized`，统计 ETA 保持主指标，AI ETA 只作建议；
- 事件只有 `confirmed` 才进入模型；过期或修改会改变 `eventFactorVersion`；
- 预测批次应记录 `model_version`、`data_end_date`、输入摘要、质量分和事件版本；
- 重点监控：预测长期 `insufficient_quality`、50,000 指标批次耗时和生产等价资源峰值。

> 当前 dev 环境未执行 50,000 指标预测性能测试，不得以 M5 的 15 项性能结果替代 M8 门禁。

## 11. 保留与归档

- 在线保留：`rt_retain_days`、`day_retain_days` 热配置；
- 执行路径：调度器每日 `archive_time`（默认 03:30）执行一次 sweep，日内数据用 `rt_retain_days`、日数据用 `day_retain_days`，均归档超期完整月分区；也可在“开放 API → 保留与归档”手工“立即归档”；
- 归档对象：完整月分区；归档文件为 gzip JSON Lines（payload v2 含日内 `ts` 与日数据修正字段）；
- 归档索引：`metric_archive_index(metric_code,biz_date,file_ref,byte_offset,row_bytes)`；
- 成功判定：`metric_archive_run.status=success`，并核对行数、文件大小与索引；只有文件与索引都写入成功后才会 `DETACH PARTITION` + `DROP TABLE` 下线在线分区，随后 `online_dropped=true`；
- 失败处置：保留在线分区不删除，修复存储/权限后重跑；同一分区按唯一键幂等，`online_dropped=true` 的分区直接跳过；
- 按需恢复：`POST /api/v1/open-api/archives/:id/restore`（页面“恢复”按钮）重建分区并流式回填，主键冲突跳过；重复恢复幂等，恢复后 `status=restored`，下次 sweep 会重新归档后再下线；
- 历史归档：`payload_version=1` 的旧归档会按 v2 重新导出后再下线，避免只剩归档时丢修正字段或日内时间戳；
- 空间监控：数据库卷、归档目录、文件对象存储容量和索引增长速度。

## 12. 沙箱加固现状

当前 Compose 已启用：

```yaml
security_opt:
  - no-new-privileges:true
cap_drop:
  - ALL
pids_limit: 512
```

Worker 自身仍保留模块白名单、无网络、工作目录写限制、CPU/内存/文件大小 rlimit 和超时终止。

gVisor/`runsc` 尚未在生产等价环境验证，因而是发布前未完成项；上线前必须验证文件 IO、内存限制、启动时延、任务隔离和故障恢复。

## 13. 常见故障与处理

| 现象 | 定位 | 处理 |
| --- | --- | --- |
| 全部采集失败，worker 不健康 | `docker logs capacity-manage-worker`、:9100/v1/health | `docker compose restart worker`；检查 WORKER_WORK_ROOT 磁盘 |
| 某流程持续 failed | 任务监控执行日志 | SQL：源库账号/网络白名单；日志：路径/格式变更（更新解析规则）；脚本：沙箱限制（见 §13.1） |
| 沙箱任务 timeout | 任务日志 status=timeout | 脚本耗时超 300s：优化脚本或调 `WORKER_TIMEOUT_SEC`（须评估调度窗口） |
| 脚本 MemoryError | 任务日志 stderr | 脚本内存超 1024MB（`CAP_MEM_LIMIT_MB`）：优化数据批量/流式处理 |
| 日汇总 failed | `daily_summary_log.error_msg` | 按错误修复后手工补跑（系统管理/运维入口 `POST /data/summary/run`，幂等） |
| 日报未生成 | `report_result` 表 status/errMsg | 手工"重新生成"（幂等）；检查 FILE_ROOT 磁盘与字体/图表资源 |
| 登录大面积 401 | Redis 连通性 | Redis 故障会失效全部会话：恢复 Redis 后用户重登 |
| 数据库慢查询 | pg 慢日志（SLOW SQL ≥200ms） | 检查是否大日期范围查询；日表按日分区，范围查询限定业务日窗口 |
| 磁盘增长快 | 日表/RT 表分区 | RT 表 90 天保留（可配）过期归档；日表在线 3 年；执行分区清理（归档后 DROP） |
| 预测任务长时间 running | `forecast_run`、backend 日志、AI 延迟 | 检查日汇总完成、AI 超时和数据量；必要时重跑，不删除成功批次 |
| API 签名 401 | 时间戳、nonce、canonical、Redis | 校时；确认请求使用原始 query/body；检查 nonce TTL 与 Redis 健康 |
| 调用 429 | `api_call_log.reason` | 检查 Key 每分钟限流和客户端重试；不得关闭调用审计 |
| AI 状态 invalid | `forecast_ai_adjustment.error_msg` | 修复 AI 凭据/网关后重算；统计预测不受影响 |
| 归档失败 | `metric_archive_run.error_msg` | 检查对象存储、磁盘权限和文件引用；在线分区保留，修复后重跑 |

### 13.1 沙箱故障说明

- 沙箱限制：模块白名单、无网络（黑名单 + 部署层网络隔离）、仅工作目录可写、超时 300s SIGKILL 进程组、内存 1024MB（RLIMIT_AS）、CPU 120s（RLIMIT_CPU）、文件 10MB（RLIMIT_FSIZE）、禁止新进程（RLIMIT_NPROC）；
- 限制失败不影响 worker 主进程（子进程组隔离）；
- 脚本调试：先在"预览试跑"（AI 试跑同沙箱）验证，再激活。

## 14. 容量参考（一期实测，详见性能测试报告）

- 日表：5 万指标 × 200 日 = 1000 万行环境下，90 天×100 指标范围查询 P95 < 0.5s；全量日报生成 ~12s；
- 写入：1 万行/日 批量写入 ~1.7 万行/s；
- 日汇总（全量指标逐指标 upsert）：5 万指标级耗时显著增长（见性能测试报告 S7 容量结论），**生产建议指标规模超过 1 万时评估批量化改造（P2）**。
