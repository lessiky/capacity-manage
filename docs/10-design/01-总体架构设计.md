## 1. 设计目标与原则

1. **闭环优先**：一期聚焦"采集 → 落地 → 预警 → 报表"闭环，覆盖 P0 需求；
2. **单体模块化**：后端为单一 Go 可执行文件，内部按业务模块强隔离（模块间仅通过接口调用，禁止跨模块直接访问表），保证可维护性同时避免分布式复杂度；
3. **扩展就绪**：数据源适配器、采集方式、清洗规则、通知渠道、LLM 服务均为可插拔接口，为二期/三期预留；
4. **安全纵深**：凭据 AES-256-GCM 加密、全程脱敏、RBAC + 数据权限、沙箱隔离、全量审计；
5. **可运维**：结构化日志、平台自检视图、热配置免重启、调度重启自愈。

### 2.1 部署形态

- 一期 MVP：**单节点**部署 `capacity-server`（API + 调度同进程）+ `python-worker` 进程池 + PostgreSQL + Redis + MinIO，全部 Docker Compose 编排；以进程自愈（restart: always）+ 每日备份保障可用性；
- 目标形态：应用节点双活（API 负载均衡，调度通过 Redis 分布式锁单主执行），数据库独立部署；
- 进程拓扑与端口：

| 进程 | 端口 | 说明 |
| --- | --- | --- |
| capacity-server | 8080 | API + 调度（内置健康检查 /healthz、/readyz） |
| python-worker | 9100 | 仅监听 127.0.0.1，供 Go 侧调用 |
| PostgreSQL | 5432 | 仅内网 |
| Redis | 6379 | 仅内网 |
| MinIO | 9000/9001 | 仅内网（API/Console） |
| Nginx（前端） | 80/443 | 静态资源 + 反向代理 /api → 8080 |

## 3. 模块划分（后端 internal/）

| 模块 | 包路径 | 职责 | 关键扩展点 |
| --- | --- | --- | --- |
| auth | internal/auth | 登录/锁定/会话超时/JWT 签发校验 | 预留企业统一身份认证（OIDC）适配器 |
| system | internal/system | 用户/角色/功能权限/数据权限/参数/操作日志 | Casbin 策略模型 |
| bizsystem | internal/bizsystem | 业务系统 CRUD、状态（正常/维护中/已下线）、资源信息 | — |
| metric | internal/metric | 指标 CRUD/停用、三级阈值、判定方向、合理性校验、调整历史 | 阈值模板（P1）、衍生指标（P1） |
| tradingday | internal/tradingday | 日历维护、前/后第 N 个交易日推导、缓存、Excel 导入导出 | 多市场（沪/深/境外） |
| datasource | internal/datasource | 数据源登记、凭据加密、连接测试、健康状态 | `DataSourceAdapter` 接口（API/监控系统预留） |
| flow | internal/flow | 流程定义与生命周期、变量替换、三类采集、清洗引擎、预览试跑 | `Collector`、`Cleaner` 接口 |
| scheduler | internal/scheduler | cron + 交易日模式调度、手工触发、重试、超时、并发控制、重启自愈 | 分布式调度（goquartz 预留） |
| judge | internal/judge | 阈值判定、水位计算、防抖（P1） | 分时段阈值（预留） |
| alert | internal/alert | 告警生成/合并、状态机、SLA 统计、静默（P1） | `Notifier` 接口（邮件/IM 二期） |
| data | internal/data | 日内/日数据落地、去重、每日汇总、查询、手工修正 | 归档策略（P1） |
| report | internal/report | 日报生成、图表数据、Excel/PDF 导出 | 报表模板/订阅（P1） |
| ai | internal/ai | LLM 适配器、脱敏、生成流程/清洗脚本、配置助手、调用审计 | `LLMClient` 接口（行内/云可切换） |
| pyworker client | internal/pyclient | 与 Python Worker 的 HTTP 调用、超时、结果解析 | — |

**模块间依赖规则**：
- 允许方向：handler → service → (persistence / 其他模块 service 接口)；
- 禁止：模块 A 的 service 直接 import 模块 B 的 persistence；禁止循环依赖（CI 用 `go vet` + 依赖检查脚本门禁）；
- 跨模块事件（如采集完成 → 判定 → 告警）通过 Go 接口回调 + 同进程事件总线（channel）完成，保留替换为 MQ 的可能。

## 4. 关键流程设计

### 4.1 采集执行流程（核心路径）

```
调度触发（cron / 交易日模式 / 手工）
  → 生成 collect_task_log（status=running, source=auto|manual|backfill）
  → 解析流程配置（flow + metric + datasource）
  → 变量替换（${biz_date}/${prev_trading_day}/${next_trading_day}/${trading_day_offset:N}/${system_code}/${hour}；日期变量支持 `:format` 后缀自定义格式, 如 ${prev_trading_day:YYYYMMDD}）
  → 按采集方式分发：
      SQL       → database/sql（只读账号，超时控制）→ 结果集列映射/聚合
      日志解析  → 本地 glob / SFTP 下载 → 正则/分隔符/JSON 解析（失败行跳过并计数）
      Python    → python-worker /v1/execute（入参 JSON → 出参 JSON，超时强制终止）
  → 清洗引擎（内置规则链：类型转换/单位换算 → 空值与异常值标记 → 去重取值；可插入脚本清洗）
  → 写 metric_value_rt（upsert，按 指标+时间戳 去重）+ 清洗留痕
  → 判定引擎（阈值/方向/水位）→ 回写判定结果 → 告警引擎（合并/生成）
  → 任务日志收尾（行数/解析失败率/耗时/错误信息）；失败进入重试策略（默认 3 次）
```

- 单流程隔离：每个流程在独立 goroutine + context 执行，失败/超时不影响其他流程；
- 并发控制：全局并发数可配置（默认 8）；
- 重启自愈：服务启动时扫描 status=running 且超过超时上限的任务置为 failed 并按重试策略处理；未触发的任务由 cron 下次自然补位，日汇总任务幂等可重跑。

### 4.2 每日汇总流程

- 每日 00:10（可配 `param.daily_summary_time`）触发；业务日期 = 前一日（自然日）或前一交易日（流程配置口径）；
- 对每个启用指标：按日内统计方式（最新/最大/最小/平均/求和）汇总前一日 metric_value_rt → 写 metric_value_day（max/min/avg/last + 水位 + 当日最高级别），日内无数据则标记 `missing`；
- 幂等：同一 (metric_code, biz_date) 重跑为覆盖更新；手工修正后日数据进入 `corrected` 状态并保留原值快照；
- 产出日报数据（report 模块消费）。

### 4.3 判定与告警流程

见《04-告警状态机与判定规则》。要点：每次采集成功落地后立即判定；同一指标同级别恢复前仅保留一条活动告警（新数据刷新 last_value/持续时长）；数据异常（采集失败重试耗尽/缺数/异常值占比超限）由采集侧独立产生 P2 告警。

### 4.4 交易日感知调度

- 调度模式两种：`normal`（标准 cron）与 `trading_day`（交易日 + 收市后窗口，如 17:30）；
- 交易日模式计算下次触发时间：从当前时间起，经日历表定位下一个（当前市场）交易日，取其窗口时点；窗口已过则顺延下一交易日；
- 推导服务带 Redis 缓存（key=market+date，TTL 24h，日历变更时主动失效）。

## 5. 安全设计

| 面 | 措施 |
| --- | --- |
| 认证 | JWT（access 2h）+ 会话超时（默认 30 分钟，Redis 会话表）；连续 5 次失败锁定 15 分钟（Redis 计数，可配） |
| 授权 | Casbin RBAC：功能权限（菜单/按钮/API 级）+ 数据权限（按业务系统的 manage/view 集合），API 层双重校验 |
| 凭据 | 数据源密码 AES-256-GCM 加密存储（密钥 `APP_CRED_KEY` 独立配置，支持轮换：双密钥过渡）；采集账号只读；页面/日志/导出脱敏（`******`，尾 4 位可见可配） |
| 审计 | 关键操作全量落 sys_operate_log（阈值/流程/修正/告警处理/权限/导出/AI 调用）；AI 调用输入输出摘要审计（ai_call_log） |
| 沙箱 | Python Worker：默认无网络、只读 FS（仅临时工作目录可写）、超时默认 5 分钟强杀、CPU/内存限制、模块白名单；入参出参/堆栈/资源占用全量记录（详见 Spike 03 与接口契约 05） |
| 传输 | Nginx TLS 终结（证书由运维提供）；内网服务间绑定内网地址 |
| 注入 | 全部 GORM/参数化查询；SQL 采集模板的变量替换仅替换白名单占位符，值来自系统上下文不可被用户注入任意 SQL（变量值转义由适配器负责） |

## 6. 性能与数据设计

- **日表 metric_value_day**：约 5 万指标 × 365 天 ≈ 1800 万行/3 年上限；按月 RANGE 分区 + 复合索引 `(metric_code, biz_date)`、`(biz_date, level)`；在线保留 3 年（可配），超期归档至 MinIO（parquet/csv，P1 任务）；
- **日内表 metric_value_rt**：设计上限 5 万指标 × 小时级 ≈ 120 万点/日 ≈ 4 亿行/月；按月 RANGE 分区 + 唯一索引 `(metric_code, ts)`；在线保留默认 90 天（可配 `param.rt_retain_days`），超期分区 DROP（归档可配，P1）；写入采用 batch insert（200 行/批）；
- **热点查询**：大盘总览走"日表当日行 + 告警计数"小查询 + Redis 缓存 30s；指标趋势 90 天单指标查询命中分区裁剪，目标 <2s（性能场景 5-2 验证）；
- **热配置**：阈值/流程/参数 = DB + 进程内缓存（TTL 30s + 写后主动失效广播），变更免重启（NFR 7.5）；
- **容量结论**：5 万指标写入/查询容量基线由性能测试 5-2 场景 7 专项验证，不达标则调整日内保留策略或引入时序存储（计划风险 7）。

## 7. 可观测与自检

- 结构化日志（slog JSON）：请求日志（traceId/耗时/状态）、调度日志、采集日志、沙箱执行日志；
- /healthz（进程存活）、/readyz（DB/Redis/MinIO 依赖检查）；
- 平台自检页（FR-ADM-08 基础版）：调度器运行状态、各数据源最近连接健康、最近日汇总执行情况、各表行数与分区存储占用；
- 运维监控接入：进程存活、接口 QPS/延迟（日志采集）、磁盘水位（日志+自检）。
