## 1. Go ↔ Python Worker（HTTP，仅 127.0.0.1:9100）

### 1.1 POST /v1/execute — 执行脚本（采集/清洗）

请求：

```json
{
  "taskId": "task-20261105-000123",
  "scriptType": "collect | clean",
  "scriptRef": { "scriptId": 12, "version": 3 },
  "scriptContent": "# 平台内联下发(与 scriptRef 二选一, 调试/预览用)",
  "params": {
    "biz_date": "2026-11-05",
    "prev_trading_day": "2026-11-04",
    "next_trading_day": "2026-11-06",
    "trading_day_offset": 1,
    "system_code": "CORE01",
    "hour": "17",
    "extra": { }
  },
  "input": { },                    // clean 类型: 原始数据 JSON
  "timeoutMs": 300000,
  "workDir": "/tmp/capworker/task-xxx"   // 唯一可写目录
}
```

响应（HTTP 200；执行失败亦为 200 + status=failed，仅协议错误用 4xx/5xx）：

```json
{
  "status": "success | failed | timeout",
  "data": [ { "metric": "log_growth", "value": 12.5, "unit": "GB" } ],
  "rowsOut": 1,
  "exitCode": 0,
  "durationMs": 4213,
  "resource": { "cpuMs": 3900, "memPeakKb": 48211 },
  "stdout": "（截断至 64KB）",
  "stderr": "（截断至 64KB）",
  "error": { "type": "ScriptError", "message": "...", "stack": "..." }
}
```

约定：

| 项 | 约定 |
| --- | --- |
| 脚本入参 | 环境变量 `CAP_PARAMS`（上述 params 的 JSON 字符串）+ `CAP_INPUT`（input JSON）；脚本从 `os.environ` 读取，不读 stdin |
| 脚本出参 | stdout 最后一行 JSON（collect: 数组或对象；clean: 同构对象数组）；非 JSON 输出视为 ScriptError |
| 超时 | Worker 子进程 `start_new_session` + 超时 `SIGKILL` 进程组；status=timeout |
| 限制 | 无网络（见 §1.2）、只读 FS（仅 workDir 可写）、模块白名单、CPU/内存 rlimit（Linux）、内存峰值采样（/proc 或 psutil） |
| 幂等 | 同 taskId 重复请求直接返回缓存结果（TTL 1h），防调度重试重复执行副作用脚本 |
| 并发 | Worker 进程池默认 4，任务队列长度 32，队满返回 503 |

### 1.2 沙箱实现（MVP：子进程 + OS 级限制）

- 启动方式：`python -I -E /opt/capacity/worker/run_worker.py <taskId>`（-I 隔离模式，禁用户 site-packages）；
- 模块白名单（bootstrap 替换 `sys.meta_path`）：`json, math, re, datetime, time, decimal, os(受限), sys, io, collections, itertools, functools, typing, logging(禁文件), csv, base64, hashlib`；黑名单硬拦截：`socket, subprocess, shelve, sqlite3, importlib, pickle, ctypes, multiprocessing`；
- 受限 `os`：仅 `environ/getenv/sep/listdir(workDir)/path 只读函数/makedirs(workDir)`，删除/重命名/执行全部抛错；
- 网络：MVP 依赖部署层（Docker network none / 防火墙）+ 黑名单双保险；生产 Linux 建议 `unshare -n` 启动子进程（gVisor 为二期加固）；
- 资源：`resource.setrlimit`（RLIMIT_AS 内存上限默认 1GB、RLIMIT_CPU 默认 120s、RLIMIT_FSIZE 10MB、RLIMIT_NPROC 0）；
- 审计：taskId 全量记录 入参摘要/出参摘要/exitCode/durationMs/资源峰值/堆栈 → 平台 collect_task_log + worker 日志文件（MinIO 归档 30 天）。

### 1.4 远程脚本采集（collectType=script，不经 Worker）

本地沙箱（§1.1）只能跑 Python 且无网络。需要到**目标业务机**上取数（磁盘/进程/本机命令）时，
用「脚本采集」：流程绑定 `type=ssh` 的**执行目标**数据源，由 Go 服务端直连目标机执行，不经过 Worker。

链路（Linux 与 Windows 同规则）：

```
加载脚本(scriptId/version) + 合并入参(内置变量 + 流程自定义参数, 同名以内置为准)
  → 建一条 SSH 连接
  → SFTP 上传 <tempDir>/capcollect-<taskId>/script.<ext> 与 params.json
  → 按 OS+语言执行命令
  → 读 stdout 最后一行 JSON
  → 删除 <tempDir>/capcollect-<taskId>（成功/失败/超时三条路径都删）
```

| 项 | 约定 |
| --- | --- |
| 执行目标 | 数据源 `type=ssh`，配置 `host/port/username/password/os(linux\|windows)/tempDir`；凭据 AES-256-GCM 加密 |
| 脚本语言 | `python` / `bash` / `powershell`（`python_script.language`），文件后缀 `.py` / `.sh` / `.ps1` |
| 入参 | 与脚本同目录的 `params.json`；含平台内置变量（biz_date/prev_trading_day/next_trading_day/hour/system_code/flow_code/metric_code）与流程 `collectConfig.params` |
| 出参 | stdout 最后一行 JSON，collect 形如 `[{"metric","value","unit"}]`；`metric` 需匹配流程指标（留空视为通用） |
| 超时 | 系统参数 `flow_timeout_seconds`（默认 300s）；跨网络只能断开会话，不能强杀远端进程组 |
| 清理 | 临时目录在执行结束后删除；删除失败写 RunLog 告警，不影响本次采集结果 |
| 审计 | RunLog 记录 status/exitCode/耗时/目标 `os(host:port)`/目录与 stdout/stderr（各截断 64KB），不落凭据 |

命令矩阵：

| OS | python | bash | powershell |
| --- | --- | --- | --- |
| linux | `python3 <path>` | `bash <path>` | `pwsh -NoProfile -NonInteractive -File <path>` |
| windows | `python <path>` | `bash <path>` | `powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <path>` |

要点：
- **路径形态差异**：Windows OpenSSH 的 SFTP 根是盘符根，上传用 `/C:/Windows/Temp/...`，执行命令用 `C:/Windows/Temp/...`；
- **脚本不从 stdin 读数据**（本地沙箱下 stdin 是脚本源）；
- **目标机需自备解释器**：Linux 需 `python3`/`bash`/`pwsh`，Windows 需 `python`/`powershell`；缺解释器表现为 stderr `command not found`；
- **清洗脚本仅支持 Python**：`scriptType=clean` 在本地沙箱执行，`language` 强制 `python`（登记非 python 清洗脚本返回 400）；bash/powershell 仅用于 `scriptType=collect` 的远程脚本采集；
- **语法校验仅对 Python 生效**：版本保存前的沙箱语法校验只跑 `language=python`（`POST /scripts/{id}/versions`）；bash/powershell 由目标机解释器执行，保存时不拿 Python 解析器校验（否则 bash 脚本会被误判，如 `invalid decimal literal`），正确性以目标机执行结果与 RunLog 为准；
- **沙箱隔离不适用**：脚本在目标机上真实执行，安全边界改为"专用只读采集账号 + 最小权限 + 脚本版本审计 + 临时目录即时清理"；
- **Windows PowerShell** 建议脚本文件方式（本实现即 `-File`），避免 stdin 编码问题；
- **Windows 脚本请用纯 ASCII**：Windows PowerShell 5.1 对无 BOM 文件按系统 ANSI 代码页读取，中文注释会乱码、个别字节还会被当作转义符导致**语法解析失败**；`.ps1` 保持 ASCII（中文说明写到脚本描述/文档），Bash/Python 在 Linux 侧 UTF-8 无此问题；
- **脚本不要依赖工作目录**：远端执行不 `cd` 到临时目录，脚本须用自身路径（`__file__`/`${BASH_SOURCE[0]}`/`$PSScriptRoot`）定位同目录 `params.json`。
- **指标名从参数取**：参考脚本按 `metric` 入参 > 平台内置 `metric_code`（当前流程绑定的指标）> 脚本默认值 的优先级决定出参 `metric`；因此同一脚本可复用到不同设备/不同指标的流程，无需改脚本。入参 `metric` 留空即自动跟随流程指标，也便于多台设备共用一份脚本。

参考脚本（读同目录 `params.json`，输出磁盘空间利用率）：
- `backend/worker/examples/collect_disk_remote.py`：Python 通用版；
- `backend/worker/examples/collect_disk_linux.sh`：Linux/Bash，入参 `mount`（挂载点或设备，默认 `/`）；
- `backend/worker/examples/collect_disk_windows.ps1`：Windows/PowerShell，入参 `drive`（盘符，默认 `C:`）。

## 2. LLM 适配器（internal/ai/llm.go 接口）

```go
type LLMClient interface {
  // Chat 单轮对话; ctx 带超时(默认 60s); 实现方负责重试(1次, 仅网络错误)
  Chat(ctx context.Context, req ChatReq) (ChatResp, error)
}
type ChatReq struct {
  Feature    string   // flow_gen / clean_gen / assistant
  Messages   []Message // [{role: system|user|assistant, content}]
  MaxTokens  int
  Temperature float64
}
type ChatResp struct {
  Content string
  Model   string
  Usage   struct{ Prompt, Completion int }
}
```

- 默认实现 `openaiCompat`：`POST {BaseURL}/chat/completions`（OpenAI 协议兼容：行内网关/通义/文心等均可适配）；
- 配置：`AI_BASE_URL`、`AI_API_KEY`（AES-GCM 加密存储于 sys_param，读取解密）、`AI_MODEL`、`AI_TIMEOUT`；
- **脱敏钩子**（必过）：`masking.SanitizeForAI(input)` 规则：
  1. 连接串 `jdbc:/mysql://...` 整串替换为 `<CONN>`；host:port 替换为 `<HOST>`；
  2. 常见凭据键值（password/secret/token/apikey 及中文"密码/口令"）值替换为 `******`；
  3. 11 位手机号、18 位身份证号、15-19 位银行卡号掩码（保留首尾 2-3 位）；
  4. 样例数据行保留结构（字段名），数值列 >10 行时截断为前 10 行 + `...`；
- 审计：每次调用写 ai_call_log（feature/user/model/input_digest 前 200 字/output_digest 前 500 字/latency/status）；
- 降级：连接失败/超时/401/429 → 返回业务错误 50300 `degraded=ai_unavailable`，前端提示"AI 服务暂不可用，请手工配置"，主流程不阻塞。

## 3. 数据源适配器（internal/datasource/adapter.go 接口）

```go
type DataSourceAdapter interface {
  Test(ctx context.Context, cfg *Config) (TestResult, error)   // 连接测试
  // db 型: 执行 test_sql(默认 SELECT 1 / DBMS 对应语句), 只读账号
  // log 型: 列目录匹配 glob, 试读首行, 校验编码
  Collect(ctx context.Context, cfg *Config, req CollectReq) (rows []map[string]any, meta CollectMeta, err error)
  Close() error
}
```

- 注册制：`registry[driver] = factory`（一期：`oracle`(go-ora)、`mysql`(go-sql-driver)、`log-local`、`log-sftp`(pkg/sftp)）；
- 凭据在 Config 中仅出现解密后的临时对象，日志打印前必须 `masking.RedactConfig(cfg)`；
- 健康巡检：调度器每 10 分钟对可用数据源执行 Test（轻量：DB ping / SFTP 列目录），连续 3 次失败 → status=abnormal + P2 告警。

## 6. 调度内部契约（scheduler ↔ flow engine）

- 调度器持有流程快照（DB 加载 + 30s 热缓存）；触发时按 `schedule_mode` 计算：
  - normal：cron 表达式（6 位含秒，robfig/cron v3）；
  - trading_day：下一交易日 + 非交易时点 window_time（单 "HH:MM"，15:00 至次日 09:00，15 分钟一个间隔；交易日日历不分市场，按 SH 口径维护）；
- 数据日期 biz_date_mode：natural=当日（默认）/ prev_day=上日（前一自然日）/ calendar=上一交易日；决定采集时 `${biz_date}` 变量取值与数据落地业务日（上一交易日按交易日日历推导，推导失败回退自然日）；
- 触发 payload = `{flowId, triggerTime, source}`；执行引擎自行加载最新流程版本（配置热生效，运行中任务用触发时快照，不中途换配置）；
- 并发控制：全局信号量（参数 collect_concurrency，默认 8）；单流程互斥（同流程上一实例未结束则跳过并记日志，不排队）；
- 超时：context.WithTimeout(参数 flow_timeout_seconds，默认 300s)；超时=timeout 状态，进重试策略。

## 7. 二期 M6 告警闭环接口契约（R2.1）

本节为二期 M6「告警闭环」新增的对外/对前端契约，级别语义、状态机与判定规则详见
《10-design/04-告警状态机与判定规则.md》V2.0。级别采用 `p1 > p2 > p3 > p4`（小写存储、
大写展示）；首次阈值命中为 P3，数据质量类告警为 P4，累积升级目标为 P2/P1。

通用约定：

- 统一响应包 `{code, message, data}`（`code=0` 成功），与一期一致；
- 时间字段一律 RFC3339 带时区；`bizDate` 为 `YYYY-MM-DD`；
- 全部写操作落操作审计（`sys_audit_log`，`module=alert`）；
- 数据权限沿用 `internal/pkg/scope`，越权返回 `CodeDataForbidden`。

### 7.1 告警升级策略 API

```text
GET    /api/v1/alert-escalation-policies            权限 alert:view
POST   /api/v1/alert-escalation-policies            权限 alert:policy:manage
GET    /api/v1/alert-escalation-policies/:id        权限 alert:view
PUT    /api/v1/alert-escalation-policies/:id        权限 alert:policy:manage
DELETE /api/v1/alert-escalation-policies/:id        权限 alert:policy:manage
POST   /api/v1/alert-escalation-policies/simulate   权限 alert:view     （不落库重放）
GET    /api/v1/alert-escalation-policies/:id/preview?metricCode=&days=30&to=  权限 alert:view
```

写入请求体（`PolicyInput`）：

```json
{
  "name": "预警线连续3天升级P2",
  "sourceLine": "warn",            // warn | danger
  "targetLevel": "p2",             // p1 | p2（warn 只能升 P2，danger 只能升 P1）
  "mode": "consecutive",           // consecutive | window_count
  "consecutiveDays": 3,            // mode=consecutive 时必填 >0
  "windowDays": 7,                 // mode=window_count 时必填
  "hitDays": 3,                    // mode=window_count 时必填，0 < hitDays <= windowDays
  "dayBasis": "natural",           // 日口径，默认 natural
  "scopeType": "system",           // global | system | metric
  "scopeValue": ["CORE01", "CORE02"],   // 多选：global=[]；system=系统编码数组；metric="系统.指标"数组
  "scopeValues": [],               // 同上（别名，二选一即可；两者都传则取并集）
  "enabled": true,
  "priority": 100
}
```

校验与约束：

| 项 | 规则 | 失败码 |
| --- | --- | --- |
| 形态 | `consecutive` 需 `consecutiveDays>0`；`window_count` 需 `windowDays>0 且 0<hitDays<=windowDays` | `CodeUnprocessable` |
| 目标级别 | `sourceLine=warn → targetLevel=p2`；`sourceLine=danger → targetLevel=p1` | `CodeUnprocessable` |
| 作用域取值 | `global` 为空数组；`system`/`metric` 至少 1 个目标；自动去空白、去重、保序 | `CodeUnprocessable` |
| 作用域越权 | 非平台管理员的多值作用域中**每一个**目标都须在自身数据权限内，任一越权整条拒绝 | `CodeDataForbidden` |
| 热生效 | 写操作后主动失效策略缓存，下一次判定即生效；不回写历史告警 | — |

作用域为多选：

- 存储 `alert_escalation_policy.scope_value` 为 **JSON 数组（jsonb）**，`global` 落 `[]`；历史单值在
  迁移 `0019_alert_policy_scope_multi` 中自动包成单元素数组；
- 指标作用域保存前把裸指标编码解析为 `系统编码.指标编码`，逐个解析、逐个校验权限；
- 匹配为「任一命中即算命中」：`system` 命中 `metric.systemCode`，`metric` 命中
  `metricCode` 或 `systemCode.metricCode`；未命中该指标的策略不参与升级判定；
- 入参 `scopeValue` 兼容单值字符串（旧调用方）与数组两种形态；响应统一返回数组。

`POST /simulate` 请求体 `{metricCode, from, to, policy}`；`GET /:id/preview` 用已保存策略在
指定指标、日期窗口上重放，返回命中日明细与逐日升级结论（用于「最近 7 天中 3 天超预警线」
的预览）。两者均不写库、不改动任何活动告警。

### 7.2 告警详情 timeline / evidence

```text
GET /api/v1/alerts/:id   权限 alert:view
```

响应体：

```json
{
  "alert": { "...": "persistence.AlertRecord（含下列二期字段）" },
  "timeline": [ { "time": "2026-10-21T01:54:34+08:00", "event": "escalate", "user": "system",
                  "detail": "级别升级 P3 → P2: 预警线最近7天命中3天",
                  "evidence": { "windowDays": 7, "hitDays": 3, "policyId": 2 } } ],
  "trendSnippet": { "day": [], "rt": [] }
}
```

`alert_record` 二期新增字段：`source_line`、`escalation_policy_id`、`escalated_at`、
`escalation_count`、`evidence_window`（JSONB，保存窗口日期与命中天数）。

`timeline` 节点 `event` 取值：`trigger`（首次触发）、`escalate`（升级或管理员确认降级）、
`downgrade_suggestion`（重放后不再满足规则的降级建议，需管理员确认，不自动降级）、
`claim`、`note`、`recover`、`close`。`evidence` 为可选对象，来自 `alert_level_history.evidence`
（不可变级别变更历史），供详情页解释「为何是当前级别」。

渠道请求体 `{name, type, config, enabled}`；`type ∈ {smtp, wecom, dingtalk, feishu, webhook}`，

Webhook 的 `secret`）。凭据以 AES-GCM 密文入库，更新时敏感项留空表示保留旧值。

且启用；`dedupWindowMin` 不得为负。同一告警同一级别同一去重窗口内只发送一次，升级（级别变化）
后允许再次发送。

静默期间照常记录告警与通知日志并写入抑制原因，不丢数据。静默判定顺序：指标级 → 系统维护 →
全局维护，均在「发送前」统一判定。

发送失败按 **1 分钟 / 5 分钟 / 30 分钟** 三次退避重试；三次均失败后给平台管理员生成 `notify_fail`
类型的 P4 渠道异常告警（同一渠道去重，避免风暴）。

### 7.5 通用 Webhook 签名与幂等键契约（发送端 → 接收端）

`type=webhook` 的渠道向 `config.target`（JSON `POST`）发送，约定如下。

请求体：

```json
{
  "event": "alert | recovered | escalate | report",
  "level": "p1",
  "alertNo": "AL20261021015434-f2813a",
```

### 8.1 统计预测与风险清单 API

```text

GET    /api/v1/forecasts/risk?days=7..90                     权限 metric:view

```

`POST /forecasts/recompute` 兼容原有查询参数写法
`?date=YYYY-MM-DD`，也可使用可选 JSON 请求体按系统或指标限定重算范围：

```json
{
  "date": "2026-10-21",
  "systemCodes": ["M7_SYS"],
  "metricCodes": ["M7_FC"]
}
```

- `date` 省略时使用当前业务日；请求体为空时仍执行全量重算；
- `systemCodes`/`metricCodes` 省略或为空数组表示不按该维度过滤，两者同时提供时取交集；
- 过滤条件未匹配到活动指标时返回 `CodeBadRequest`；
- 响应保留批次原字段，并增加 `scoped`、`scopeMetricsTotal`、`scopeMetricsDone`、`scopeMetricsSkipped`
  表示本次筛选范围的产出计数。

`GET /forecasts/risk` 的 `days` 范围为 7~90。窗口不大于 30 天时优先使用 30 天预测，
大于 30 天时优先使用 90 天预测；首选时窗未命中时回退另一时窗。响应项中的
`horizonDays` 固定为实际选中的 `30` 或 `90`。AI 调整可用时，风险项还返回
`aiStatus`、`aiRationale`、`adjustmentNote`、`suggestedEtaWarnDate` 和
`suggestedEtaDangerDate`；主 ETA 仍采用统计预测结果。

`GET /metrics/:code/forecast` 返回单指标指定 horizon 的最新预测结果（`MetricForecast`）：

```json
{
  "metricCode": "M7_FC",
  "horizonDays": 30,
  "runId": 1,
  "modelType": "linear",
  "status": "success",
  "etaWarnDate": "2026-11-02",
  "etaDangerDate": "2026-11-16",
  "slope": 0.42,
  "intercept": 71.3,
  "residualStd": 0.08,
  "confidence": 0.845,
  "dataQuality": 0.8,
  "riskScore": 0.5,
  "explanation": "线性模型拟合近 29 个有效日，趋势上升，预计预警线最早日期为 2026-11-02",
  "curve": [{ "bizDate": "2026-10-21T00:00:00Z", "value": 75.9, "lower": 75.7, "upper": 76.1 }]
}
```

状态语义（`status`）：

| 状态 | 含义 |
| --- | --- |
| `success` | 正常产出预测曲线与 ETA |
| `never` | 趋势方向与阈值方向不符（如 `higher_worse` 且斜率不为正），不产出 ETA |
| `insufficient_data` | 有效点低于门槛（30 天 <14 点、90 天 <30 点） |
| `insufficient_quality` | 质量分缺失或 <0.8，不输出确定性 ETA |

约定：

- `horizon` 仅接受 `30`/`90`，缺省 `30`；
- ETA 为预测曲线首次越过阈值的最早业务日，未命中为 `null`；
- 置信区间为残差标准差推出的 95% 区间，容量类下界截断到 `0`；
- `riskScore` 使用可复现公式 `0.40*到线紧迫度 + 0.30*趋势强度 + 0.20*模型置信度 + 0.10*数据质量`，
  紧迫度以预测起点（最后一个有效数据日）到 ETA 的天数计；
- 同一 `inputDigest`（输入序列 + 模型版本 + 事件版本）重复执行必须产生相同数值结果。

### 9.3 请求签名与防重放

启用 `signatureRequired` 后，开放接口必须携带：

| 请求头 | 约定 |
| --- | --- |
| `X-API-Key` | `{keyId}.{secret}` |
| `X-Cap-Timestamp` | Unix 秒，与服务端偏差不得超过 5 分钟 |
| `X-Cap-Nonce` | 16~128 字符，调用方每次请求生成唯一值 |
| `X-Cap-Signature` | 小写 hex HMAC-SHA256 |

规范化字符串（各字段以 `\n` 连接）：

```text
timestamp
nonce
METHOD
path
rawQuery
sha256(body)
```

签名：

```text
hex(HMAC-SHA256(secret, canonical))
```

服务端使用 Redis `SETNX` 对 `apikey:nonce:{keyId}:{nonce}` 保存 10 分钟。签名错误、时间戳超窗、nonce 长度非法或 nonce 重放均返回 401；Redis 不可用时签名请求 fail closed。

- 调度器每日 `archive_time`（默认 03:30）按保留期分别处理日内与日数据，日内用 `rt_retain_days`、日数据用 `day_retain_days`；
- `POST /archives/run` 处理超期完整月分区，可用 `table=metric_value_rt|metric_value_day` 只处理单表，`retainDays`/`rtRetainDays` 覆盖默认保留期；响应 `archivedPartitions`（日数据）与 `rtArchivedPartitions`（日内）分别计数；
- 归档文件为 gzip JSON Lines（payload v2 含日内 `ts` 与日数据修正字段），`metric_archive_run` 记录运行状态、文件、`online_dropped` 与 `payload_version`，`metric_archive_index` 按指标+业务日建立索引；
- 只有归档文件与索引全部写入成功后才执行 `DETACH PARTITION` + `DROP TABLE` 下线，失败时保留在线分区；`online_dropped=true` 的分区幂等跳过；
- `POST /archives/:id/restore` 按归档记录重建分区并流式回填，主键冲突跳过（幂等），成功后 `status=restored`、`online_dropped=false`；
- `GET /archives/query` 返回 `source=archive`，在线与归档数据查询边界由业务日决定。

批量导入支持 `multipart/form-data` 的 CSV 文件或 JSON 数组。CSV 表头：

```text
metricCode,name,systemCode,unit,judgeDirection,warnLine,dangerLine
```

导入运行状态为 `success/partial/failed`，并返回逐行失败原因。`GET /metrics/imports` 支持 `page`、`pageSize`（默认 20，最大 200），返回 `items/total/page/pageSize`。

扩展项状态约定：

- 衍生指标支持停用后重新启用；停用状态下不可试算，只有停用后允许物理删除；
- 阈值模板支持停用后重新启用；停用状态下不可套用，只有停用后允许物理删除；
- 采集侧的单位/线性/取整转换统一由采集流程的 `clean_config.transforms` 配置，随流程版本生效，无独立规则接口。
