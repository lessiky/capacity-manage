# 容量管理平台测试计划

- **版本**：V1.0（M0 交付物，WBS 0-6）
- **编制日期**：2026-10-14
- **依据**：《容量管理平台开发计划》§6 测试与质量保证、WBS 0-6；《容量管理平台需求文档》§7 非功能性需求
- **状态**：待评审发布（M0 验收项）

## 1. 目的与范围

验证一期（M0~M5，2026-11-02 ~ 2027-06-04）交付物满足《需求基线 V1.0》定义的功能与非功能要求，确保 M5 准出标准（功能 + 性能 + 安全全部达标且 UAT 签署）可执行、可度量。

- **在测范围**：后端 REST API、前端页面、采集引擎（SQL/日志/Python 三类）、调度与重试、数据落地与汇总、告警闭环、大盘与报表、AI 辅助能力、性能、安全。
- **不在范围**：外部系统（Oracle/MySQL 实例、SFTP 服务端、大模型服务）自身功能正确性，仅验证本平台与其接口/协议对接的正确性与故障行为。

## 2. 测试策略（对应计划 §6.1）

| 层级 | 内容 | 准入标准 | 准出标准 |
| --- | --- | --- | --- |
| 单元测试 | BE 核心逻辑（判定/清洗/交易日推导/调度）与 FE 关键组件 | 代码合入 develop | 核心模块行覆盖率 ≥70%，一般模块 ≥50%，CI 门禁拦截 |
| 接口测试 | REST API 契约与异常分支 | 模块代码冻结 | 主要接口自动化覆盖 ≥80%，用例全部通过 |
| 功能测试 | 三轮（M2/M3/M4 节点 + 发布前全量回归） | 对应模块接口测试通过 | P0/P1 缺陷清零，遗留 P2 ≤5 且有规避方案与风险评估 |
| 性能测试 | §4.4 八场景逐项验证 | 功能测试（第三轮）通过 | 全部达标 |
| 安全测试 | 凭据脱敏、权限越权、注入、会话、AI 审计 | 功能测试（第三轮）通过 | 无高危漏洞 |
| UAT | 2~3 个试点系统端到端试运行 2 周 | SIT 全量通过、性能/安全通过 | 业务侧签署验收 |

**覆盖率度量**：BE 使用 `go test -cover` + `gotestsum`/`gocov` 生成行覆盖率报告；FE 使用 Vitest + `@vitest/coverage-v8`。报告随每次 CI 构建留存，按模块归档月度汇总。核心模块清单：`judge`（三级阈值判定）、`tradingday`（交易日推导）、`flow`（调度/重试/超时）、`pkg/aesgcm`（凭据加密）、`pkg/masking`（脱敏）、`variables`（交易日变量引擎）、`scheduler`。

**现状（M0）**：BE 单元测试已全绿（`go test -count=1 ./...`），覆盖 judge/tradingday/flow/aesgcm/masking/variables 核心路径；FE 测试脚手架于 M1 引入。

## 4. 测试层级设计

### 4.1 单元测试

- **核心模块（行覆盖率 ≥70%）**：`judge`、`tradingday`、`flow`、`pkg/aesgcm`、`pkg/masking`、`variables`、`scheduler`。
- **一般模块（≥50%）**：`persistence`、`auth`、`report`、`app` 路由装配。
- **用例设计要点**：表驱动；边界值（阈值等于判定线、结果集 0 行/1 行/多行、重复行、非交易日、跨月/跨年、缺数日）；异常路径（连接失败、超时、脏数据）。
- FE 关键组件（阈值视图、水位进度条、告警状态机展示）于 M1 起补充 Vitest 用例。

### 4.2 接口测试

- **工具**：BE 侧 Go（`httptest` + `internal/testutil` 内存 SQLite + 假 RESP）做契约测试，随 `go test` 进 CI；SIT 侧集成测试用 pytest + requests（或 Newman/Postman 集合），指向 sit 环境真实栈。
- **覆盖目标**：`/api/v1/*` 全部主要接口（auth、admin/*、systems、metrics、datasources、flows、tasks、alerts、reports、ai、dashboard）契约 + 异常分支（40100/40101 未认证、40300/40301 越权、404 资源不存在、50300 降级）。主要接口自动化覆盖 ≥80%。
- **契约校验**：响应 envelope（`{code,message,data,traceId}`，成功 code=0）、分页参数、字段命名（camelCase）、时间格式；与 `docs/10-design/03-API规范.md` 逐项比对。
- 自动化套件纳入 CI 的 SIT 阶段，MR 合入前必跑（develop 分支）/每日定时（main 分支）。

### 4.3 功能测试

- **轮次与节点**：第 1 轮 M2（采集引擎：数据源/流程/调度/沙箱）；第 2 轮 M3（数据落地 + 告警闭环）；第 3 轮 M4（大盘报表 + AI）；发布前全量回归（M5）。
- **关键场景矩阵**（按模块，优先级 P0）：
  - 系统管理：登录/连续 5 次失败锁定 15 分钟/会话 30 分钟超时登出；RBAC 功能权限 + 按系统数据权限；操作日志检索与导出；重置密码。
  - 业务系统：建档（编码唯一）、编辑（负责人变更同步数据权限）、维护中告警静默、已下线冻结采集。
  - 交易日：日历 Excel 导入/导出/手工标记；推导（前/后/第 N 个交易日、跨年）；交易日模式调度 + 收市后窗口（如 17:30）。
  - 采集：连接测试（DB 测试 SQL / 日志列目录试读一行）；预览试跑；cron 与交易日两种频率；失败重试与超时（单流程 ≤5 分钟可配置）；Python 沙箱（超时强杀/无网络/工作目录写限制）；缺数检测与缺数告警；任务监控与执行日志。
  - 数据落地：日内数据点去重；每日汇总（00:10，max/min/avg/last）；水位计算（百分比/绝对值 + 判定方向）；手工修正（原因必填、原值保留、留痕）。
  - 告警：三级判定（正常/预警/危险）；告警合并与内容；数据异常告警；认领/处理/关闭状态机与 SLA 统计。
  - 报表与大盘：日报自动生成（超线清单/采集异常清单）；Excel/PDF 导出；报表数据权限；大盘 TOP10 下钻、趋势 7/30/90 天与阈值参考线。
  - AI：生成采集流程/清洗脚本 → 人工审阅 → 预览试跑 → 保存生效；样例脱敏验证；AI 服务不可用时降级纯手工配置（不影响主流程）。
- **执行方式**：手工为主，冒烟与回归关键路径（登录 → 建档 → 采集 → 落地 → 告警 → 日报）脚本化。

### 4.4 性能测试（计划 §6.2，基线 = 需求 7.1）

**工具**：k6（用户/流量模拟）、PostgreSQL 自带工具与 `EXPLAIN`（DB 侧基线）；数据准备脚本化（`testing/data/perf`）。

| # | 场景 | 目标 | 验证方法 |
| --- | --- | --- | --- |
| 1 | 20 并发用户常规操作 | 响应 <3s（95 分位） | k6 恒定并发 20，混合操作（查询/编辑/导出各占比） |
| 2 | 大盘/列表首屏 | 加载 <3s（95 分位） | k6 首屏接口时序（overview → systems → 详情） |
| 3 | 日级任务全部完成（调度时效） | ≤30 分钟（试点实际量与 10 倍外推双口径） | 全量流程定时触发，记录首启→全部完成；10 倍外推用造数脚本 |
| 4 | 数据写入：日增量 ≥1 万行，连续 30 天 | 无性能劣化、无数据丢失 | 造数 + 每日写入，抽样对账行数与值 |
| 5 | 查询：千万行级日表范围查询、单指标 90 天趋势 | 单次查询 <2s | 造数至千万行，p95 计时 + 执行计划检查（索引命中） |
| 6 | 全量指标日报生成 | <60s | 造数至全量指标规模，计时端到端 |
| 7 | 设计上限评估：5 万指标 × 小时级采集（约 120 万点/日） | 记录实际写入/查询基线，输出容量结论 | 写入/查询基线实测 + 容量外推报告（不要求达标，要求结论） |
| 8 | Python 沙箱：超时终止、内存限制、无网络 | 均生效，且不影响主进程 | 恶意脚本（死循环/大内存/外联）注入验证，复跑 spike 03 用例 |

- **基线管理**：每轮性能测试记录环境画像（CPU/内存/磁盘/Docker 版本/PG 版本与参数），与上轮基线对比输出劣化判定；M5 前在生产等价硬件上复测场景 1/2/5。
- **准入**：功能第三轮通过；**准出**：场景 1~6、8 达标，场景 7 输出容量结论。

### 4.5 安全测试

| 项 | 测试点 | 方法 |
| --- | --- | --- |
| 凭据脱敏 | API 响应/运行日志/导出文件无明文密码；DB 中凭据为密文（AES-GCM）；日志中的连接串/密钥键值自动打码 | 抓包 + 日志扫描 + DB 抽查 + 用例注入（在错误日志里故意写入 `password=xxx` 验证 masking） |
| 权限越权 | 水平越权（业务负责人访问他系统数据/告警/报表）；垂直越权（普通用户调 admin 接口） | 双账号交叉操作 + 接口直调 |
| 注入 | SQL 注入（指标 SQL 模板变量、搜索框）、命令注入（Python 脚本入参）、XSS（系统名称/备注等富文本回显） | sqlmap（只读模式）+ 手工 payload |
| 会话 | JWT 篡改/过期/重放；锁定后登录拦截；会话超时登出；并发登录策略 | Burp Suite / 手工 |
| AI 审计 | 提供给模型的数据样例不含凭据与敏感业务数据；AI 调用日志（输入输出摘要）完整可审计；AI 不可用降级 | 构造含凭据样例验证拦截/脱敏 + 日志审计抽查 |

**准出**：无高危漏洞；中危漏洞有整改计划与责任人；安全测试报告归档。

### 4.6 UAT

- **对象**：2~3 个试点系统（M0 附录 A 确认接口人与数据）；**周期**：M5 内连续 2 周稳定试运行。
- **内容**：试点系统日常全流程（采集 → 落地 → 告警 → 认领处理 → 日报导出），业务侧真实操作口径。
- **机制**：每日缺陷例会；UAT 缺陷按 §6 时限响应；收敛标准 = P0/P1 清零。
- **签署**：UAT 通过由业务侧代表签署验收单（M5 交付物）。

## 5. 用例管理

- **ID 框架**：`TC-<模块>-<3 位序号>`。模块代码：`ADM`（系统管理）/`SYS`（业务系统）/`MET`（指标阈值）/`COL`（采集）/`TD`（交易日）/`DAY`（数据落地）/`MON`（监控告警）/`RPT`（报表大盘）/`AI`/`API`（接口）/`PERF`（性能）/`SEC`（安全）。示例：`TC-MET-001`。
- **用例字段**：ID、模块、需求映射（FR 编号）、优先级（P0~P3）、前置条件、步骤、预期结果、适用环境、实际结果、状态（未执行/通过/失败/阻塞）。
- **存放**：一期用 Git + Markdown，`testing/cases/<模块>/TC-<模块>-NNN.md`（同文件可含多用例）；如引入 Jira，用例同步迁移并保留 ID 不变。
- **需求追溯**：基线 P0 清单每条 FR 至少 1 条用例，追溯矩阵于 M2 末输出并纳入 M5 验收材料。

## 6. 缺陷管理

- **严重级别**：P0 阻塞（主流程不可用/数据错误）/ P1 严重（功能错误有规避）/ P2 一般（体验/边缘场景）/ P3 轻微（建议）。
- **响应时限**：P0 4 小时、P1 当日、P2 2 个工作日内、P3 下一迭代排期（与计划 §6.3 一致）。
- **状态流**：新建 → 确认 → 处理中 → 已修复 → 回归通过 → 关闭；回归不通过可重开（reopen 计数并复盘）。
- **机制**：UAT 期间每日缺陷例会；周报输出缺陷统计（新增/关闭/老化/趋势）；P0/P1 缺陷 100% 回归验证。

## 7. 质量门禁（与计划 §6.3 对齐）

- 静态扫描：SonarQube 无新增 blocker/critical（M1 接入 CI）。
- MR：评审 100%，关键模块（采集引擎/判定/凭据安全）至少 2 人审批。
- CI 门禁：`go vet` + `go test`（含覆盖率阈值检查）+ 前端构建；develop 合入前必过。
- 发布门禁（M5 准出）：功能三轮 + 性能 + 安全全部通过且 UAT 签署。
