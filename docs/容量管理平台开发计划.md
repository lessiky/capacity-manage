## 1. 计划概述

### 1.1 计划目标

基于需求文档 V1.1，编制容量管理平台的整体开发计划，覆盖：团队组织、技术方案、工作分解与工作量、里程碑排期、测试策略、发布与试点、风险管理及已确认事项（第 9 节）。

一期（MVP）核心目标：跑通"交易日感知的采集 → 数据落地 → 监控预警 → 报表分析"闭环，覆盖 2~3 个试点业务系统，实现容量数据自动化采集、三级阈值标准化管理与主动预警，替代人工执行 SQL 与翻查日志。

### 1.2 实施范围（分阶段）

| 阶段 | 范围 | 目标 |
| --- | --- | --- |
| 一期（本计划重点） | 全部 P0 需求：业务系统管理；指标与三级阈值管理；交易日管理；数据库/日志两类数据源与 SQL/日志解析/Python 脚本三类采集方式 + 清洗 + 调度；每日数据落地；监控大盘 + 阈值判定 + 平台内告警展示与处理；日报 + 趋势 + 导出；AI 辅助采集与清洗；系统管理 P0 项 | 跑通"交易日感知的采集 → 落地 → 预警 → 报表"闭环，覆盖核心业务系统 |
| 二期 | 告警对外推送（邮件/IM、分级通知、超时升级）、防抖与静默窗口、数据质量检查与历史补采、报表中心（模板/周期/订阅推送）、开放 API、归档策略、批量导入、衍生指标与阈值模板、基础趋势外推与预测报表 | 补齐告警闭环与报表订阅，保障数据质量 |
| 三期 | AI 辅助容量预测与预测报表、短信渠道、衍生指标与阈值模板增强、CMDB/ITSM 集成、数据源扩展（API 等）、多租户预留 | 从"监控告警"走向"预测与规划" |

> 阶段划分以需求文档第 8 节为准，并按"P0 = 一期范围"的定义做了少量调整，调整事项均已确认（见第 9 节），按计划处理落实。

### 1.3 关键假设

1. 团队按第 2 节配置到位，2026-11-02 启动；
2. 开发/测试/UAT/生产环境与基础资源由运维方提供（见 3.4）；
3. 试点业务系统（2~3 个）在 Phase 0 确认，业务侧提供指标口径、采集 SQL/日志样例与数据源只读账号；
4. 平台部署环境到各源数据库、日志服务器的网络可达性在 M2 里程碑前完成；
5. AI 大模型服务（行内或经授权云 API）可用，并满足数据安全合规要求；
6. 交易日日历（沪/深市场）由业务侧或交易所官方公告提供，可覆盖当年及次年；
7. 排期已含约 2 周法定节假日缓冲（含 2027 年春节）。

### 1.4 开发原则

- **基线先行**：第 9 节 6 项事项已全数按"计划处理"确认，Phase 0 完成需求评审并正式签署基线；后续范围变更走变更流程；
- **关键路径优先**：采集引擎是一期关键路径，优先保障资源并设置中期检查点；
- **试点驱动**：以 2~3 个试点系统端到端验证全流程，避免一次性大规模铺开；
- **扩展就绪**：数据源适配器、清洗规则、通知渠道、AI 服务均按可插拔扩展点设计，为二期/三期预留。

## 3. 技术方案概要

### 3.1 总体架构

与需求 3.1 业务架构分层一致（展示/服务/数据/采集/数据源层），一期采用"单体模块化"后端 + 独立 Python Worker 的部署形态：

```
展示层    Vue3 Web 管理端：大盘 / 报表中心 / 告警中心 / 指标管理 / 采集流程 / 任务监控 / 系统管理
服务层    Go（Gin，单体模块化）：
          系统服务 | 指标与阈值服务 | 交易日服务 | 采集服务 |
          调度服务 | 判定与告警服务 | 报表服务 | AI 辅助服务
数据层    PostgreSQL（业务配置 + 日内/日数据，按月分区） | Redis（缓存/会话/交易日缓存）
          | MinIO（导出文件/脚本版本/报表文件）
采集层    数据源适配器（DB / 日志-本地 / 日志-SFTP） | 流程引擎（变量替换、SQL、日志解析）
          | Python 沙箱 Worker（独立进程池） | 清洗引擎（内置规则 + 脚本） | cron 调度（交易日感知）
数据源层  业务数据库（SQL） | 日志文件（本地 / SFTP） | （预留：API / 监控系统）
辅助服务  LLM 服务（行内优先，适配器可插拔） | （二期：SMTP / IM 网关）
```

### 3.2 技术选型

| 类别 | 选型 | 选型理由 / 说明 |
| --- | --- | --- |
| 后端框架 | Go 1.22+（Gin） | 轻量、高并发、内存占用小、单二进制部署，适合采集调度与大量沙箱进程管理场景；数据库采集走 database/sql + 驱动（JDBC 等价语义） |
| ORM / SQL | GORM + 手写 SQL | GORM 处理常规 CRUD，复杂查询手写 SQL（大数据量区间查询） |
| 安全框架 | JWT + Casbin | RBAC 功能权限 + 数据权限、会话超时、登录锁定 |
| 前端框架 | Vue 3 + TypeScript + Vite + Element Plus | 生态成熟，适配 1920×1080 管理端 |
| 图表 | ECharts 5 | 趋势线 + 三级阈值参考线、仪表盘、TOP N、超线区间标注 |
| 数据库 | PostgreSQL 14+（备选 MySQL 8） | 日表千万行级，月分区 + 复合索引 |
| 缓存 | Redis 7 | 交易日推导缓存、大盘热数据、会话与登录失败计数 |
| 调度引擎 | robfig/cron（v3，条目持久化） | 支持 cron、动态增删与热配置、重试与超时控制；一名单节点，预留分布式调度（goquartz 等） |
| Python 沙箱 | 独立 Python 3.11 Worker + OS 级进程隔离 | 见 3.3-1；二期可升级 gVisor / 容器隔离 |
| 文件存储 | MinIO（或本地磁盘） | 导出文件、脚本版本、报表文件、归档数据 |
| AI 服务 | LLM REST API（行内或经授权云） | 适配器模式，地址/模型可配置，不可用时自动降级手工 |
| 导出 | Excelize + go-maroto | Excel（明细 + 图表）、PDF（图文版式） |
| 部署 | Docker + Docker Compose（MVP），预留 K8s | 数据库每日备份、按日恢复 |
| CI/CD | Git + GitLab CI / Jenkins | 单测 + 静态扫描门禁，dev / sit / uat / prod 四环境 |
| 监控与日志 | 结构化日志 + 接入现有运维监控 | 进程、接口、磁盘自检（FR-ADM-08 基础版） |

> 备选说明：若团队技术栈偏好 Java / Python 系，可评估 Spring Boot / FastAPI 方案，但调度与沙箱架构需重新论证，本计划按 Go 栈编制。

### 3.3 关键技术设计

1. **Python 脚本沙箱（关键风险点，Phase 0 必须完成 Spike）**：
   - 脚本注册、版本管理与生效版本切换在平台内完成；采集/清洗脚本运行于独立 Python Worker 进程池，Go 侧经本地 HTTP 调用；
   - 隔离手段：默认无网络访问（网络命名空间/防火墙白名单，可配白名单）、只读文件系统（仅临时工作目录可写）、超时强制终止（默认 5 分钟，可配）、CPU/内存限制、依赖模块白名单；
   - 脚本按约定接收系统变量（含前一交易日）作为入参、按 JSON 约定格式输出；入参/出参、异常堆栈与资源占用全量记录执行日志；
   - MVP 采用子进程 + OS 级限制；gVisor / 容器级隔离作为二期加固项。
2. **凭据安全**：数据库密码、SFTP 密码 AES-256-GCM 加密存储，密钥独立配置并支持轮换；页面/日志/导出全程脱敏，禁止明文落盘；采集账号仅授只读权限。
3. **交易日引擎**：交易日日历表支持多市场（沪/深/境外）；推导服务统一提供"前/后第 N 个交易日"并缓存结果；变量替换引擎统一支持 ${biz_date}、${prev_trading_day}、${next_trading_day}、${trading_day_offset:N}、${system_code}、${hour}；调度服务对交易日模式在计算下次触发时间时直接定位下一交易日及收市后窗口（如 17:30）。
4. **判定与告警状态机**：告警状态机"活动 → 处理中 → 已恢复/已关闭"（关闭后仅可备注）；同一指标同级别恢复前仅保留一条活动告警（合并防重复，新数据仅刷新记录）；判定结果回写日内数据点；数据异常（P2）告警由采集侧独立产生（采集失败/缺数/异常值占比超限）。
5. **数据量与分区设计**：
   - 日数据表：按"指标 + 业务日期"唯一，复合索引（指标 + 日期、日期 + 级别），在线保留 3 年（约 1000 万行，查询性能不显著劣化）；
   - 日内数据点表：按"指标 + 时间戳"唯一（去重依据），按月分区，在线保留默认 90 天（可配置），超期归档；
   - 设计上限验证：5 万指标 × 小时级采集 ≈ 120 万点/日，由性能测试（5-2）专项验证写入与查询性能，若不达标则调整日内保留策略或引入时序存储。
6. **热配置**：阈值、采集流程、模板与全局参数采用"DB + 本地缓存 + 变更通知"机制，修改后免重启生效（NFR 7.5）。
7. **流程级隔离与调度**：单流程失败/超时不影响其他流程；调度并发数可配置（默认 8）；日级采集任务全部在 30 分钟内完成；服务重启后自动恢复未完成任务。
8. **AI 辅助架构**：AI 服务为可插拔适配器（行内/经授权云）；输入数据样例强制脱敏（不含凭据与敏感业务数据）；生成结果经"人工审核 → 预览试跑 → 版本保存"后生效，支持一键回滚；调用日志（输入/输出摘要）全量可审计。

### 3.4 部署架构

- 环境链路：dev → sit（集成） → uat → prod；
- MVP 部署：应用节点 2 台（双活，含 Python Worker） + 数据库节点独立部署；一期可先单节点上线（以进程自愈 + 每日备份保可用性），双活为目标形态；
- 备份恢复：数据库每日全量备份，上线前及每季度至少 1 次按日恢复演练；
- 自监控：进程、接口、磁盘、调度状态接入运维监控，平台自检页提供平台内视图。

### 6.3 质量门禁与缺陷管理

- 代码：静态扫描（SonarQube）无新增 blocker/critical；MR 评审 100%（关键模块至少 2 人审批）；
- 发布门禁：M5 准出 = 6.1 功能 + 性能 + 安全全部通过且 UAT 签署；

## 7. 发布与试点推广计划

1. **试点选择**（Phase 0 确认）：2~3 个业务系统，覆盖数据库 + 日志两类数据源、百分比 + 绝对值两种阈值表达方式，并至少包含 1 个核心级别系统；
2. **推广步骤**：UAT 试运行（1 周） → 生产 1 个试点系统（1 周） → 全部试点系统（2 周） → 内部验收发布；
3. **发布方式**：版本号 + 发布说明 + 回滚预案（迁移脚本版本化、旧版本镜像保留、数据回滚脚本）；
4. **上线检查单**：源系统账号只读权限核查、网络白名单、当年及次年交易日日历、阈值初始数据、用户账号初始化、备份策略启用；
5. **运维交接**：运维手册、监控接入（进程/接口/磁盘）、备份按日恢复演练 1 次。

## 12. 项目管理机制

- **迭代**：双周迭代、周演示（M2/M3/M4 节点向业务方演示）；
- **会议**：每日站会（15 分钟）、周会（进度/风险/下周计划）、需求评审与变更会（按需）；
- **工具链**：需求与缺陷 Jira（或等价工具）、代码 Git（main/develop/feature 分支策略）、评审 100%；
- **风险**：风险清单（第 8 节）每周更新，月度向项目发起人汇报；
- **变更**：基线后的范围变更须走"影响评估（工期/工作量） → PM 与发起人批准 → 基线更新"；
- **验收**：M5 由 PM 组织验收，参与方含业务侧（试点系统）、运维与项目发起人。
